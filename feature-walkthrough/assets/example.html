One export, even after repeated clicks.

Repeated requests for the same report and options now reuse an active export job. Users can click again without starting another copy through this sequential request path.

Same action. Different result.

Illustrative scenario: a user submits the same report and options again while the first export is still active.

Before

The handler creates job A, then creates job B for the repeated request. Both jobs process the same export.

After

The handler creates job A. The repeated request finds A still active and returns its ID. Different options still start a separate job.

Follow the request

  1. Validate.
    Check the requested report and export options.
  2. Find a match.
    Look for an active job with the same report and options.
  3. Reuse or create.
    Return the match; otherwise create and enqueue a new job.

A completed job is not active. A later export can therefore create a new job.

Why match both report and options?

Two requests for the same report can ask for different output formats. Reusing a job based only on the report could return the wrong file. The match includes the options that determine the export.

What evidence would establish this behavior?

What remains risky, and what would rollback restore?

Two simultaneous requests might both see no active job and both create one. Sequential reuse alone does not establish concurrency safety.

Reverting this hypothetical handler change would restore the earlier selection behavior. It would not remove jobs already queued or undo exports already delivered.
